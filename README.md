## Library description

Library Requirements is a Modelica package to formally define requirements and checking them automatically when a model is simulated. An overview of this library is given in the publication [Formal  Requirements Modeling for Simulation-Based Verification](http://www.ep.liu.se/ecp/118/067/ecp15118625.pdf) 

In order to define properties and requirements mostly a 2-valued logic is used. There are some functions and blocks based on 4-valued logic using type Property (Violated, Undecided, Satisfied, Undefined -- since version 0.8.0, with the extended temporal logic of EDF's ReqSysPro / CRML), especially block Requirement. Furthermore, there are cast-operators to map 2-valued to 4-valued logic and vice versa. 4-valued logic is used to define (a) if a property is not applicable (Undefined: only relevant in a certain situation, and outside it), (b) if a property is applicable but not yet decided (Undecided), and (c) if a requirement was not tested in a simulation run. Undefined is the neutral element of `and4` / `or4`; the algebra is not a lattice (absorption and distributivity fail), so Property expressions are never simplified. 

In this package the standard convention is used that names of memory-less operators (implemented as Modelica functions) start with lower-case letters and names of operators with memory (implemented as Modelica blocks) start with upper-case letters.
 
This package uses basically Modelica 3.2 language elements and requires the Modelica Standard Library 4.1.0 (`uses(Modelica(version="4.1.0"))` since version 0.7.1). Earlier versions used a Modelica extension in some examples (but not outside of examples) to pass a model instance as argument to a function whose input is a record, to associate requirements in a reasonably convenient way with behavioral models, expecting the cast of a model to a record to enter the language and the tools. The cast did enter the language (Modelica Language Specification 3.6, section 12.6.1: `R(m)`), but of Dymola, OpenModelica and Modelon Impact only Dymola implements it, so since version 0.7.1 the examples build their observation records with explicit record constructors, which every tool runs (see below). Earlier versions of this library contained also examples utilizing the proposed new Modelica language element to "call a block as a function". These examples had been removed.

The current version of the library uses a buffer for the implementation of sliding windows (Internal.SlidingWindow). The size of this buffer is fixed to 20 (constant nBuffer in package SlidingWindow). If the buffer is too small for a requirement from package ChecksInSlidingWindow, then a warning is printed. The result of the requirement verification might then not be correct. 

**This package is not yet finalized. A redesign is planned. The redesigned library (with improved implementations of models and new functionality) should be backwards compatible to this version, but it is not guaranteed. If non-backwards compatible changes are introduced, most likely automatic conversions will not be provided.**

## Changes in version 0.12.0 (October 2026)

**Violation statistics** (ModCheck's requirements plan, section 24). For a long run -- an annual building simulation, a duty cycle -- a verdict alone does not say enough: a requirement violated once for a second and one violated every summer afternoon are both *violated*. The new block `Verify.ViolationStatistics` takes a check's `property` and (optionally) its `margin` and answers three questions: how often was the requirement violated (`nViolations`, episodes of `property = Violated`, merged within `mergeGap` and counted from `minDuration`), for how long in total (`totalDuration`, `violatedFraction`) and at most (`longestDuration`, `tLongestStart`), and what was the worst violation and when (`worstMargin`, `tWorst`, also per episode). The worst margin is found at every local extremum of the margin by extending the MSL's `Modelica.Blocks.Math.ContinuousSignalExtrema`, or with a ratchet that fires only at a new low, cheaper for an oscillating margin. `Verify.Requirement` and `BooleanRequirement` compute the same statistics with `computeStatistics = true`, log them as a `Statistics` line beside the verdict, and `PrintViolations` prints them. The check blocks still have no accumulators; no existing output, log line or regression reference changed. `Examples.Elementary.ViolationStatistics` asserts every output against closed-form values. Full account: `UsersGuide.ReleaseNotes.Version_0_12_0`.

## Changes in version 0.11.0 (September 2026)

**Eigenvalue predicates over a linearisation** (ModCheck's requirements plan, section 22.7). A linearisation is a tool operation, not a simulation, so no check model computes a plant's eigenvalues inside the run that produces them; the new package `LinearAnalysis` reads the state matrix from the MATLAB v4 file ModCheck's orchestrator writes beside every linearisation (`readStateMatrix`, through `Modelica.Utilities.Streams.readRealMatrix`; the URI resolved in a parameter of its own and the matrix read in an initial equation, because Optimica folds `loadResource` at translation and refuses an impure function there), folds its eigenvalues into modes with the same integrator rule and parasitic cut as ModCheck's `linear_checks.py` (`modes`, LAPACK's `dgeev` directly: OpenModelica 1.27 cannot generate code for `Modelica.Math.Matrices.eigenValues` in a parameter context), and evaluates the predicates as constants over a nominal run -- `EigenvalueCheck` (`Types.EigenMetric`: a real-part, damping, frequency or time-constant bound over every mode, optionally in a frequency band) and `EigenvaluesWithinRegion` (a polygon of the (Re, Im) plane) -- each with `Property` and `margin`. ModCheck's generated `EigenCheckFromFile` models carry one block per eigenvalue requirement and its orchestrator compares their outputs with the Python record: the R3 cross-check, never the reported verdict (agreement on every corpus item on OpenModelica and Modelon Impact). The frequency-response family has no Modelica side, by decision. `Examples.Elementary.LinearAnalysis.SecondOrder` asserts the blocks on the shipped `Resources/Data/SecondOrderLinearization.mat` (identical margins on both tools). No existing block changed. Full account: `UsersGuide.ReleaseNotes.Version_0_11_0`.

## Changes in version 0.10.0 (September 2026)

**Step-response metrics** (ModCheck's requirements plan, section 21). `SignalAnalysis.StepResponse` computes the running metrics of a response after a step of a signal, sampled at `samplePeriod` (at the half-periods, off a result grid of the same period): the step as a change between two samples, its window to the next step or `T_window` after it, the target the stepping signal or a reference input (`Types.StepTarget`), the peak, the level crossings interpolated between samples, the last exit from the settling band, the deviation, the extrema beyond the target and the damping and decay ratios from them. `ChecksInFixedWindow.StepResponseCheck` bounds one metric (`Types.StepMetric`: overshoot, undershoot, rise time, delay time, settling time, steady-state error, damping ratio, decay ratio) and emits `Property` and `margin` -- Undefined before the first step, Undecided from the step to the earliest sample the bound is provably met or broken, decided at the window's close otherwise, the margin following the running metric. The reported verdict of a step-response requirement is ModCheck's `step_checks.py` on the stored trajectory (rule R7); the blocks are the development aid in a Modelica tool and the cross-check ModCheck runs beside it. `Examples.Elementary.StepResponse` asserts the blocks against the closed forms of a second-order step response and a disturbance. No existing block changed. Full account: `UsersGuide.ReleaseNotes.Version_0_10_0`.

## Changes in version 0.9.1 (September 2026)

**The CSV reader's derivative at the file's last row.** `Internal.CSV.getRealDer` returned 0 at the last row of a MA-HS-CSV file (as beyond the file's range, where the row is held), so a check model reading a file to its end saw every derived signal drop to 0 in its final stored row. It now returns the slope of the segment ending at that row; the Python reader (`mahscsv.Signals.slope` in ModCheck) changed the same way and the ctypes test probes the last row. Full account: `UsersGuide.ReleaseNotes.Version_0_9_1`.

## Changes in version 0.8.0 (September 2026)

**Four-valued `Property`.** `Types.Property` gains a fourth value, `Undefined` (appended, Integer value 4): the property is *not applicable*, as distinct from `Undecided`, which now means *applicable but not yet decided*. The operators are the extended temporal logic (ETL) of EDF's ReqSysPro / CRML: `LogicalFunctions.and4`, `or4`, `not4` (the 16-entry tables), `and4All`, `or4All` (folds seeded with Undefined, the neutral element), `cardUndefined`; `PropertyAnd` / `PropertyOr` / `PropertyNot` delegate to them (an unconnected `nu = 0` block is Undefined); `PropertyToBoolean` gains `undefined = false`; `forall3` is superseded by `and4All`. Every check block of `ChecksInFixedWindow` emits Undefined while its condition is false (was Undecided); the FFT checks are Undefined before their first trigger. `Verify.Requirement` / `PrintViolations` collapse the four values to violated / untested / satisfied and log **attempts** beside each verdict, the number of phases in which the property was applicable. `Examples.Elementary.LogicalBlocks.PropertyTable4` asserts all tables and documents the laws that fail (absorption 12 of 64, distributivity 6 of 64, complements): the algebra is not a lattice, and Property expressions must never be simplified by Boolean rewriting. Full account: `UsersGuide.ReleaseNotes.Version_0_8_0`.

**Margins** (version 0.9.0). Every check block exposes `margin` = *robustness*/`scale`: the signed distance of the check to its limit in the quantity's unit (≥ 0 exactly when the check holds), divided by the new parameter `scale`, the requirement's tolerance (default 1, the raw robustness) -- 1 is one tolerance of headroom, < 0 a violation by that many. `Interfaces.MarginOutput` is the connector type; `During` and the `When*` blocks take the robustness as the input `rho` (the caller writes `u - limit`; `When*` samples it at the deciding edge), the duration blocks expose their running `duration`, the count blocks their `countRising`, the sliding-window, frequency, domain and FFT blocks divide the quantity they already had. `LogicalFunctions.marginAnd` / `marginOr` fold margins over the applicable (not Undefined) properties. No accumulators: the worst margin over a run and its instant are taken from the stored trajectory (ModCheck plan section 18.5, rule R2) -- or, since 0.12.0, computed during the run by the separate, opt-in `Verify.ViolationStatistics`. `Examples.Elementary.Margin` asserts every family against closed-form values; each example is a regression case with the margins stored. The signal-based two-run design behind the MA-HS-CSV reader transfers to any FMI- or SSP-based tool: the simulation and the checking engine are separate tools joined by one file of named signals. Full account: `UsersGuide.ReleaseNotes.Version_0_9_0`.

## Changes in version 0.7.1 (September 2026)

A maintenance release with no change in requirement semantics: the library now runs in a third Modelica tool, Modelon Impact, and all 68 examples were simulated with Dymola 2026x, OpenModelica 1.27.1 and Modelon Impact and compared tool against tool with the [ModCheck](https://github.com/MBILLC/ModCheck) regression harness. Every change was checked to leave the Dymola and OpenModelica results of every example unchanged. The full account, with the comparison table, is `UsersGuide.ReleaseNotes.Version_0_7_1`.

* **`uses(Modelica(version="4.1.0"))`.** No change in the library was needed for the Modelica Standard Library 4.1.0.
* **Verdict without `terminal()`.** `Verify.PrintViolations` has two new parameters on its Advanced tab, `useEvaluationTime` (default `false`) and `evaluationTime`. The verdict of a requirement model is taken and printed at `terminal()`; a tool that does not support the operator (Modelon Impact evaluates it to `false`) never printed it. With `useEvaluationTime = true` the verdict is taken at `evaluationTime` instead; every example sets `evaluationTime` to its StopTime, so switching the option on is all such a tool needs.
* **`LogicalBlocks.FallingEdgeTerminate.delay`** (default 0): the simulation terminates that long after the falling edge instead of at it, for a tool that stores only the pre-event state at a `terminate()` instant and would otherwise drop the verdict taken at that very edge.
* **The FFT checks (`ChecksInFixedWindow_withFFT`) run in Modelon Impact.** Four independent causes, each fixed in a form that leaves Dymola and OpenModelica bit-identical: sized local arrays in `Internal.checkDomain`; an explicit start of the sampling chain, `(condition and not pre(condition)) or (initial() and condition)`, for a tool that does not honour the initial equation `pre(condition) = false`; the new `delay` on the terminating edge; and the evaluation chain of `WithinRelativeDomain` and `MaxTotalHarmonicDistortion` as one function call (`Internal.checkRelativeDomain`, `Internal.checkTHD`) instead of eight equations in one when-clause, which a tool that evaluates a when-body with pre-event values got wrong.
* **`LogicalFunctions.card*`** reduce over the indices instead of over the elements; the same count, and it scalarizes in Modelon Impact.
* **Observation records are built with explicit record constructors.** `Examples.MotorsWithLosses` and `Examples.SimplePumpingSystem.CheckPumpingSystem` passed model instances to their binding functions, which only Dymola accepts; the Modelica-legal record cast `R(m)` is likewise Dymola-only (measured). The call sites now spell out the constructors, `MotorData(VaNominal=dcpm1.VaNominal, ..., inertiaRotor=InertiaData(w=dcpm1.inertiaRotor.w))`, which all three tools run. Two consequences: `DCMotorWatching`'s nominal values are no longer `parameter` and the current limit in `DCMotorRequirements` is a `BooleanExpression` like the speed limit (a record with parameter components returned by a function is continuous-time to Impact and over-determined to OpenModelica); and the source and sink observations use the `Source` record constructor directly, `SourceObservation_from_PartialSource` being removed, because OpenModelica 1.27.1 silently returns zeros from a function whose result is a record with an array component when the call has parameter variability.

* **`Units`** (September 2026): `Units.NonSI` type definitions and `Units.Conversions` functions in the manner of `Modelica.Units`, for the units the Modelica Standard Library lacks and that requirements in engineering practice use -- ms, mm, cm, km, ft, kft (thousands of feet), g, kg/min, ft/s, ft/min, kPa, mbar, kW, kJ; `from_<unit>` to SI and `to_<unit>` back, inlined. A generated check model writes every quantity of a requirement as `from_<unit>(<value as written>)` and converts a plant variable that is in a non-SI unit into an SI output that keeps the original as `displayUnit`, so the conversion is one factor in one place. `Examples.Elementary.Units.Conversions` asserts every factor.

**Three tools compared.** Dymola simulates 60 of the 68 examples (8 refused by the license used, "too complex for the current license"); OpenModelica 48 (20 do not build: the 14 sliding-window examples, "No runtime support for this record assignment", and the 6 FFT examples, "lowerWhenEqn: equation not handled"); Modelon Impact all 68. On the 45 examples OpenModelica and Dymola both run, every continuous signal agrees to better than 1e-4 of its range and every Boolean and Property signal switches at identical instants. On the 63 examples with a Dymola or OpenModelica reference, Modelon Impact passes all 296 signal checks.
